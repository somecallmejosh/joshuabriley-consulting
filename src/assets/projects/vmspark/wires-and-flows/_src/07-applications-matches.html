  1. Everyone arrives at this screen with the same question — where is this submission. So state is the top-level filter rather than a column you sort, the same call made on the listings grid, and the counts give a recruiter the size of each pile before they open it.
  2. Proposed matches and inbound applications share one queue because the recruiter's next action is identical either way: call the person, then move the status. What differs is provenance, so the row records whether the candidate chose this job or the system suggested them — a match carries no consent yet, and treating the two as the same thing is how candidates get submitted without being asked.
  3. A bare score gives a recruiter nothing to act on. Showing which criteria matched and which did not turns the ranked list into a work queue — 74% with the licence failing is a call to the licensing team, while 68% with the specialty failing is a rejection. The system proposes; the column is what lets a person dispose.
  4. Matching runs entirely on the vocabulary resolved upstream in Data Mapping, so an unmapped specialty cannot be scored at all. The row stays visible and says why rather than quietly ranking last, because this is the point where mapping debt stops being untidy and starts being a candidate nobody was shown for a live requisition.
  5. Bulk actions carry the selection count in the verb rather than beside it, so intent is unambiguous at the moment of the click. Status and notes stay inline — those are internal and cheap to undo.
  6. Submitting writes back to the VMS and is visible to the facility within seconds, so it is the one action that gets a confirmation and it names both the count and the destination. The rule was to make the correct path easier than the incorrect one: the dialog docks under the queue instead of covering it, so the rows being submitted can still be read while deciding.
