Entry / terminal Step Async job Branch Commit Delivered Failed Hand-off Design note
  1. The vendor payload is written down verbatim before anything tries to read it. That is what makes a bad ingest replayable rather than something you have to ask a VMS to send again — and several of them will not. It also means every downstream failure can be reproduced from a row in the database instead of reconstructed from a log line.
  2. Skipped is a recorded outcome, not silence. A source that re-pushes the same eight thousand listings every hour would otherwise make a healthy run look identical to a dead one. Counting the no-ops is the only way an operator can tell a quiet pipeline from a stalled one.
  3. A single source push can carry thousands of listings, so nothing here can happen inside a request. That constraint sits upstream of every screen in the product: it is why the grid shows states rather than progress bars, and why no button in the UI is allowed to promise a result.
  4. A listing whose facility, profession or specialty has no ATS counterpart does not raise — it lands in failed and waits. Storing failure as a state rather than throwing it as an exception is what turns the mapping queue into a workload somebody can be held to, instead of an alert somebody dismisses.
  5. The pipeline ends by writing back to the ATS, which is the honest description of what VMSpark is: a translation layer between two systems of record, owning neither. Any design that treats VMSpark's own copy as authoritative is wrong by construction, however convenient it would be.
  6. None of the band above could be touched — the rebuild ran in four phases with the pipeline left exactly as it was, and shipped no pipeline regressions. So the design work was entirely about surfacing states it had no power to change: processed, failed and skipped become tab counts on one screen, rather than a success view with the failures filed somewhere nobody opens.
