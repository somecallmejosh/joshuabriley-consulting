Entry Step System step Branch Commit Resolved Degraded Design note
  1. Rules belong to an account, not to the pipeline. Without them every client request lands as a conditional inside code that runs for all of them, so the twentieth client's edge case becomes a regression risk for the other nineteen. This screen is the escape hatch that keeps the shared path shared.
  2. Precedence is the row order and nothing else, because an earlier rule can settle an outcome the later ones never see. Order implied by creation date leaves an operator no way to change a decision except deleting a rule and writing it again, so dragging is the whole affordance rather than a convenience.
  3. A rule runs against real recent listings before it can be saved, and the preview reports how many it touched. A rule that silently rewrites four thousand records is the failure this design exists to prevent — the same reasoning that makes the backfill queued rather than synchronous, applied one step earlier.
  4. Turning a rule off and seeing whether the complaints stop is the actual debugging move, so a disabled rule stays in the list in its own position rather than disappearing. Deleting it throws away the ordering that made it wrong, which is usually the thing worth reading.
  5. A rule that matches nothing looks identical to one that works until somebody checks, so the match count sits beside it. Most reports of "the rule isn't firing" turn out to be a condition that has never once been true, and establishing that otherwise takes a database query.
  6. The engine's semantics were not ours to change — the same evaluator, the same coercion, the same three kinds of result. The design work was making an existing thing legible and safe to operate, which is a narrower claim than redesigning it and the honest one.
