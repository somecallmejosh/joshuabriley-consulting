Written on failure — nothing is dropped status: failed · failed_name · failed_event_type · raw_utterance · translation · audio_url · spoken_at · account_id
  1. A parse the system cannot resolve is written rather than dropped — status: failed plus the flag that says which half broke, alongside the raw utterance, its translation and the audio. The sidebar badge is the whole promise: she spoke it, so the system owes her an answer. The alternative is a parent asking about a nap that was never recorded.
  2. The original clip is kept and replayable. Correction means re-hearing the moment rather than reconstructing it from memory four hours later, and the provider usually only needs the two seconds around the name — hence a scrubber and a speed control on a four-second recording.
  3. The failed utterance renders as word chips, and tapping the word that was the name appends it to that child's phonetic alias list. So the same mishearing routes correctly forever after. This is the sheet's whole argument: a correction is not a fix to one record, it is a permanent improvement to recognition for that name — repair work compounds instead of repeating. The copy also gives her permission to skip it, because a guess stored as an alias is worse than no alias.
  4. Partial understanding is shown, not discarded. The parser almost always gets something, so splitting understood from not-understood means filling one gap rather than re-entering the event. The spoken time carries through untouched — an event corrected at 3pm still happened at 12:40, and overwriting that with the moment of correction would quietly falsify the attendance record.
  5. Removing an event hides it; it does not destroy it. Attendance history feeds tax records and licensing audits, so deletion is a display decision rather than a data one — and the undo is honest about that rather than pretending the row is gone.
  6. Forty-seven clean events collapse behind one line, so the screen is a work queue instead of a log viewer. The success rate sits next to it deliberately: without it, three visible failures read as a broken feature rather than the exceptions they are.
